# 07. Спайки

Три коротких исследования, результаты которых определяют решения. Каждый оформляется отчётом `docs/spikes/Sx-report.md` (что проверили, цифры, вывод, принятое решение) и ADR в `docs/decisions/`. Харнесы лежат в `tools/spikes/sx-*/`.

Разделение работы: всё, что можно проверить на этой машине, проверяй сам. Для остального (реальный Photoshop, Orange Pi, GPU AMD, телефон) напиши харнес и пошаговую инструкцию, занеси в `docs/STATUS.md` → «Нужно от человека» и иди дальше по зависящим от результата задачам.

## S1. Растровый PSD: слои, порядок, Photoshop

**Вопрос:** получается ли сгенерировать PSD с растровыми слоями нужного порядка (сверху вниз: `Notes`, `Raw` скрыт, `Clean`), который открывается в Photoshop без предупреждений, и какой библиотекой. Текстовых слоёв в MVP нет; их проверка вынесена в S1b ниже.

**Что сделать**
1. Харнес на Node: сгенерировать тестовые PSD кандидатной библиотекой (`ag-psd`) по структуре из `docs/04-psd.md` §2. Варианты:
   - V1: страница 2000×3000, три слоя (`Notes` с альфой, `Raw` скрыт, `Clean`);
   - V2: все допустимые комбинации галочек (только `Clean`; `Raw` + `Clean`; только `Notes`; и т. д.);
   - V3: высокая страница (например, 1600×10000) — для замера памяти и времени;
   - V4: `Notes` с `notes_opacity` меньше 100 и PNG с частично прозрачными пикселями.
2. Прочитать результат обратно (`readPsd`): дерево слоёв, имена, порядок, видимость, размеры и непрозрачность.
3. Подготовить `docs/spikes/S1-checklist.md` для тайпера (ниже) и пакет файлов `out/`.
4. Замерить время и пик памяти генерации (на этой машине; повтор на Orange Pi — часть S3).

**Чеклист для проверки в реальном Photoshop** (версию Photoshop записать в отчёт):
- [ ] файл открывается без ошибок и предупреждений;
- [ ] имена и порядок слоёв верные: `Notes` сверху, под ним `Raw`, внизу `Clean`; `Raw` скрыт;
- [ ] `Notes` сохраняет прозрачность (клин виден под ним), непрозрачность слоя соответствует настройке;
- [ ] слои совпадают с размером документа и не сдвинуты;
- [ ] включение `Raw` показывает оригинал без искажений, цвета не изменились;
- [ ] файл сохраняется из Photoshop и открывается повторно;
- [ ] приложить скриншот панели слоёв.

**Критерий успеха:** все пункты чеклиста выполнены на V1 и V2; V3 укладывается в разумное время и память. **Если нет:** проверить другую библиотеку, а при необходимости написать минимальный писатель PSD для растровых слоёв (формат документирован) и зафиксировать решение в ADR.

**Результат:** выбранная библиотека, ограничения, цифры производительности, ADR.

### S1b. Текстовые слои (после MVP, сейчас не делать)
Понадобится, когда придёт время включить галочку «Текст»: те же проверки для редактируемых текстовых слоёв (абзацный и точечный текст, кириллица, 40 слоёв) плюс запасной путь через `apply-text.jsx` (дизайн в `docs/04-psd.md` §3 и §6). В MVP не выполняется.

## S2. Модели на gfx1031: layout → кропы → OCR

**Вопрос:** как работает конвейер анализа на целевом железе в режиме «OCR по кропам» и какие настройки брать.

**Что сделать** (нужны машина клинера и тестовые страницы в `test_data/`, 4–8 штук)
1. Поднять окружение сайдкара по locks из `reference/bench/` (Python 3.12, ROCm-колёса, модели по revision).
2. Реализовать CLI `komaflow-sidecar analyze` с этапами `layout` и `ocr` (каждый в отдельном процессе), режимом `--overlay` и режимами OCR «кропы» и «целая страница».
3. Замерить: время layout на страницу; время OCR на кроп и на страницу; **пик VRAM по этапам**; освобождается ли VRAM между этапами; время первого запуска и второго (прогрев и кэш MIOpen); поведение при открытом интерфейсе Tauri (запас VRAM).
4. Определить `class_map`: прочитать `id2label` layout-модели и сопоставить с `bubble | sfx | onomatopoeia | text`; зафиксировать правила для неизвестных классов.
5. Подобрать `ocr_padding_px` (пробы 0, 4, 8, 16) и порог детекции: сохранить overlay-картинки и JSON для просмотра человеком; сравнить результат OCR на 5–10 боксах.
6. Проверить CPU-режим layout как запасной.

**Критерий успеха:** конвейер проходит без OOM на целевой видеокарте; в типичной странице layout + OCR занимают разумное время (ориентир ≤ 60 с суммарно); пик VRAM по этапам < 11 ГБ; VRAM возвращается после этапа; результат OCR на кропах не хуже, чем на целой странице.

**Результат:** отчёт с таблицей замеров, `class_map`, выбранные параметры, примеры overlay, ADR (в том числе по режиму OCR).

## S3. Сервер на Orange Pi Zero 3 (ARM64)

**Вопрос:** укладывается ли сервер в железо Orange Pi, какой SQLite-драйвер и кодек PNG брать.

**Что сделать**
1. Минимальный сервер (Fastify + SQLite + argon2 + кодек PNG) и скрипт `tools/spikes/s3-arm/run.sh`, который проверяет сборку и запуск на Armbian/Debian ARM64 (Node актуальной LTS) без компилятора на устройстве.
2. Проверить нативные модули: `better-sqlite3` против встроенного `node:sqlite`, argon2 (нативный или WASM), `sharp` против `pngjs`.
3. Подобрать параметры argon2: время логина 0,3–0,5 с.
4. Замерить: RSS в покое и под нагрузкой (3 параллельных клиента: GET blob + PATCH + sync); загрузку blob 30 МБ через nginx; задержки записи SQLite (WAL) на SD-карте, p95.
5. Прогнать генерацию PSD из S1 на Orange Pi (страница 2000×3000): время и пик памяти.

**Критерий успеха:** логин < 1 с; RSS под нагрузкой < 400 МБ; загрузка 30 МБ < 20 с по LAN; генерация страницы PSD ≤ ~30 с и < 300 МБ. Если PSD не укладывается — решение «собирать PSD в браузере» (см. `docs/04-psd.md` §8) выносится человеку для утверждения.

**Результат:** отчёт, выбор SQLite-драйвера и кодека PNG, параметры argon2, ADR.

## Порядок и зависимости
S1 и S3 независимы; S3 использует харнес S1 для замера PSD. S2 независим и требует машину клинера. Контракт и сервер (этап M1) можно начинать, не дожидаясь спайков: решения S1/S3 влияют на генератор PSD и выбор драйверов, но не на контракт и схему данных.
