### Пометки в клине (ADR 0017)
- Инструмент «Пометка» (N) во вкладке «Клин»: отдельный прозрачный слой поверх клина, обычная кисть со своим цветом, Shift стирает, галочка «пометки» скрывает слой. Undo общий с клином. При сохранении слой становится пометками страницы, но только если на нём рисовали (стёрли всё — пометки удаляются). При публикации пометки уходят на сервер, в PSD это слой `Notes`.
- Проверено в браузере: штрих, Ctrl+Z/Y, скрытие, сохранение («сохранено — пометки»), публикация → у страницы на сервере появился `notes_hash`.

### Повторное исправление (вечная «загрузка модели», клин в сборке)
- **Вечная загрузка модели.** Вероятная причина: команды шли в процесс модели через stdin. На Windows поток, ждущий чтения из канала, блокирует проверки этого дескриптора (`isatty` при импорте torch/transformers). Заглушки в тестах так не делают, поэтому тесты проходили. Теперь связь идёт через локальный сокет, stdin = /dev/null, у загрузки есть таймаут, ошибки содержат хвост лога модели.
- **Клин в сборке («Failed to fetch»).** Первое исправление было неполным: декодирование шло через `fetch(blob:)`, который тоже запрещён CSP. Теперь картинка декодируется без сетевых запросов (`createImageBitmap`), в CSP добавлены `blob:` и `data:`.
- **Диагностика:** `komaflow-sidecar doctor` прогоняет все модели (холодный и прогретый запуск, парковка) с таймаутами и сохраняет отчёт. В собранном приложении включены DevTools (Ctrl+Shift+I). Инструкция — `docs/DIAGNOSTICS.md`.
- Не проверено на реальном железе: исправление зависания — гипотеза, отчёт `doctor` её подтвердит или опровергнет.

### Исправления десктопа и прогретые модели (ADR 0016)
- **Модели остаются загруженными** между запусками (воркер на модель). Перед запуском другой модели на видеокарте простаивающие переносятся в ОЗУ, а не выгружаются. Выход после часа простоя.
- **`tauri build`: клин не открывал страницу («Failed to fetch»).** Причина — CSP собранного приложения запрещал `fetch` к `asset:`. Исправлено двумя способами: CSP дополнен, а клин читает файлы через IPC (`read_file`) и от CSP не зависит.
- **`tauri dev`: анализ не запускался.** Вероятная причина: в dev-сборке ресурсы сайдкара не попадают в `target/debug`, Python не находил `komaflow_sidecar`, ошибка запуска молча терялась. Теперь в dev берутся исходники из `sidecar/` репозитория (или `KOMAFLOW_SIDECAR_SRC`). Лог движка пишется в `%LOCALAPPDATA%\komaflow\sidecar\logs\sidecar.log`. Ошибка запуска и кнопка «Перезапустить движок» видны на стартовом экране, ошибки анализа, OCR и LaMa — в строке статуса.
- **После перезапуска не показывались картинки старой главы.** Разрешение asset-протокола не сохраняется между запусками. Теперь при открытии главы разрешаются папки её файлов (`allow_files`).
- Проверено здесь: тесты сайдкара (прогрев, парковка, отмена — 24 pytest), UI десктопа в браузере (статус движка, клин через `readFile`). Rust-часть по-прежнему не компилировалась на этой машине.

## Известные проблемы
- e2e на Playwright не настроены: ключевые сценарии проверены вручную (см. выше) и компонентными тестами.
- Rust-часть десктопа не компилировалась (нет тулчейна); возможны мелкие ошибки API крейтов — исправлять по выводу `cargo`.
- Диалога «Установка движка» в UI десктопа нет: движок ставится командой `komaflow-sidecar install` (см. `sidecar/README.md`).
- OCR по целой странице (запасной режим из спеки) не подключён; только по кропам.
- В режиме разработки (Vite HMR) правка кода редактора сбрасывает несохранённое состояние вкладки — в собранном приложении этого нет.
- Пик RSS при экспорте не ограничивается явно; одна страница 2000×3000 ≈ 120 МБ буферов. Подтвердить на Pi (S3).
