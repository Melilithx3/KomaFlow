# 05. Десктоп (Tauri) и сайдкар (Python)

Десктоп — Windows-приложение клинера. В MVP это **редактор разметки и шлюз публикации**, а не редактор клина.

## 1. Что делает десктоп в MVP

1. Открывает главу: из папки с raw-страницами или с сервера («Загрузить с сервера»).
2. Запускает анализ (layout → кропы → OCR) и показывает найденные объекты.
3. Даёт править разметку: боксы, типы, порядок чтения, оригинальный текст.
4. Импортирует клин (папка PNG) и необязательные пометки для тайпера (папка прозрачных PNG).
5. Публикует главу на сервер и подтягивает флажки и комментарии, оставленные в вебе.

Чего нет: кисти, ластика, LaMa, любого редактирования пикселей.

## 2. Экран

Три области: слева список страниц (миниатюры; статусы «проанализирована», «есть клин», «опубликована», «изменена после публикации»), по центру холст, справа список объектов и инспектор выбранного объекта.

**Холст.** Pan (пробел + перетаскивание или средняя кнопка), zoom колесом к курсору, «вписать» (F). Боксы с цветными номерами по типам. Редактирование: выделение, перемещение, ресайз за маркеры, рисование нового, удаление, правки стрелками (1 px, с Shift 10 px).

Палитра типов (с разной формой подписи, чтобы не полагаться только на цвет): `bubble` синий `#2563eb`, `sfx` красный `#dc2626`, `onomatopoeia` оранжевый `#d97706`, `text` зелёный `#16a34a`.

**Горячие клавиши:** `V` выбор, `R` рисовать бокс, `1–4` тип выбранного, `Del` удалить, `Ctrl+Z / Ctrl+Y` отмена/повтор, `A` авто-порядок, `O` режим «расставить порядок кликами», `[` и `]` предыдущая/следующая страница, `F` вписать, `Ctrl+S` сохранить локально.

**Порядок чтения.** По умолчанию `rtl` (из настроек проекта). Алгоритм «авто» — простая эвристика: сгруппировать боксы в строки по перекрытию по вертикали (больше 50 % высоты меньшего бокса), строки сверху вниз, внутри строки справа налево для `rtl` (слева направо для `ltr`). Чистая функция в `packages/contract`. Результат всегда можно перетащить вручную в списке или кликами в режиме `O`.

**Инспектор объекта:** тип, координаты, `source_text` (редактируемый, кнопка «Перечитать OCR» для одного бокса), индикаторы флажка и комментарий из веба (только чтение).

## 3. Архитектура клиента

- **Состояние отдельно от холста.** Хранилище состояния (страницы, объекты, выбор, история) — единственный источник истины. Холст — только рендерер, подписанный на состояние; не хранит данных. Это жёсткое требование: на этой основе позже появится редактор клина.
- **Команды с undo/redo.** Все правки — объекты-команды (`AddObject`, `MoveObject`, `ResizeObject`, `DeleteObject`, `SetType`, `Reorder`, `SetSourceText`, `ApplyAnalysis`, `ImportClean`…) с `do/undo` и ключом слияния для непрерывных жестов (перетаскивание — одна запись). История ограничена (≈200) и хранится на главу.
- **Локальный workspace** `%LOCALAPPDATA%/komaflow/workspaces/<chapter_id>/`: `workspace.json` (глава, ссылка на сервер, версия формата), `pages/<page_id>.json` (разметка страницы, `server_markup_rev`, ссылки на файлы с хэшами), `images/` (кэш скачанных blob'ов), `thumbs/`. Автосохранение с дебаунсом ~1 с, запись атомарная (tmp + rename), восстановление после сбоя при запуске.
- **Происхождение объекта:** `origin: 'auto' | 'manual'` и `touched`. Повторный анализ страницы заменяет только автоматические нетронутые объекты и показывает подтверждение.
- Работа с файлами и сетью на стороне Rust: выбор папок, перечисление изображений, потоковый SHA-256, потоковая загрузка blob'ов с событиями прогресса, токен в Windows Credential Manager (crate `keyring`). JSON-запросы к API — через плагин HTTP Tauri (без CORS).

## 4. Потоки

### 4.1 Анализ
Очередь страниц, фоновое выполнение, прогресс по страницам и этапам, отмена. Результат применяется командой `ApplyAnalysis` (откатывается одним Ctrl+Z). Кнопки: «Анализировать страницу», «Анализировать главу».

### 4.2 Импорт клина и пометок
Выбор папки PNG. Сопоставление со страницами по имени файла без расширения; запасное правило — по числовому суффиксу. Показывается таблица: совпало, нет файла, лишний файл, **размер не совпадает с raw** (такие не применяются). «Применить» привязывает файлы (путь + хэш). Аналогично для пометок (папка с прозрачными PNG).

### 4.3 Публикация
1. Выбрать проект и главу на сервере (или создать).
2. Посчитать хэши (raw, clean, notes) и сгенерировать миниатюры (WebP ~400 px по ширине).
3. Показать сводку: новые и изменённые страницы, добавлено/перемещено/удалено объектов, число файлов к загрузке.
4. `POST /blobs/check` → загрузка недостающих (2–3 параллельно, повторы с нарастающей паузой, прогресс).
5. `POST /chapters/{id}/sync`. При `BLOBS_MISSING` — докачать и повторить. При `REVISION_CONFLICT` — диалог: «Загрузить версию сервера (локальные изменения будут потеряны)» или «Перезаписать сервер» (повторный sync с актуальными `base_markup_rev`, показав, что будет затёрто).
6. Обновить локальные `server_markup_rev`, показать итог.
Прерванная публикация безопасно повторяется с того же места.

### 4.4 Загрузка с сервера
`GET /chapters/{id}` → для каждой страницы `GET /pages/{id}` и недостающие blob'ы по хэшам → собрать workspace. Текстовые данные (перевод, комментарий, флажок) хранятся рядом для показа и не редактируются.

### 4.5 Флажки из веба
Каждые ~60 с при активном окне и после публикации подтягиваются флажки и комментарии; объекты с флажком отмечаются значком, комментарий виден в инспекторе. Это единственный обратный поток данных.

## 5. Работа без сайдкара
Если сайдкар не установлен или нет подходящего бэкенда, приложение полностью работает вручную: боксы рисуются, `source_text` вводится руками. Анализ и «Перечитать OCR» отключены с понятным пояснением.

## 6. Настройки
Адрес сервера (по умолчанию `https://komaflow.tlinmo.site`), вход (логин/пароль; токен сохраняется в Credential Manager, имя устройства — имя компьютера), состояние сайдкара и моделей, выбор бэкенда (`auto | rocm | cpu`), каталог моделей, отступ кропа для OCR, порог детекции.

## 7. Требования к производительности
- Плавные pan/zoom (цель 60 fps) на странице 2000×3000 со 100+ боксами; перетаскивание боксов без лагов.
- Любая тяжёлая операция (анализ, хэширование, загрузка) не блокирует интерфейс.
- Запуск приложения до готовности редактора — единицы секунд; открытие главы из 20 страниц — без полной загрузки изображений в память (лениво, миниатюры из кэша).

## 8. Упаковка
Сборка установщиком Tauri (NSIS или MSI) под Windows x64. Python-окружение **не вшивается**: ставится при первом запуске (см. §10).

# Сайдкар

## 9. Роль и интерфейс

`sidecar/` — Python-пакет `komaflow_sidecar`: локальный сервис для моделей. Десктоп запускает его как дочерний процесс и общается по HTTP на `127.0.0.1` со случайным портом и одноразовым токеном в заголовке. Тот же код доступен как CLI (нужен для спайка S2 и отладки).

```
GET  /health          -> { ok, version }
GET  /capabilities    -> { backends: [{id:'rocm'|'cpu', available, device?, arch?}],
                           models: { layout:{installed,revision}, ocr:{…}, lama:{…} } }
POST /jobs            -> { job_id }
   { kind:'analyze_batch', pages:[{page_id, image_path}],
     options:{ backend:'auto'|'rocm'|'cpu', layout_threshold, ocr_padding_px, class_map } }
   { kind:'ocr_boxes', image_path, boxes:[{id, box}], options:{…} }
GET  /jobs/{id}       -> { state:'queued|running|done|failed|cancelled', stage, progress:{done,total}, result?, error? }
DELETE /jobs/{id}     -> отмена
```

**Результат `analyze_batch`:** по каждой странице `objects: [{ type, box, score, source_text }]`, `timings`, `backend`. Объекты возвращаются в порядке детекции; порядок чтения расставляет десктоп.

CLI-эквивалент: `komaflow-sidecar analyze --pages <dir> --out <dir> [--backend auto|rocm|cpu] [--stages layout,ocr] [--overlay]` (`--overlay` сохраняет картинки с номерами боксов для проверки глазами).

## 10. Окружение и установка

- Основа — бенчмарк пользователя `reference/bench/`: оттуда берутся locks (Python 3.12, torch + ROCm, пакеты), версии моделей по commit hash (`bench/catalog.py`), создание окружений через `uv` (`bench/envs.py`), адаптеры (`bench/worker/adapters/`) и обходные решения. Не переписывай их с нуля: адаптируй.
- Первый запуск: диалог «Установка движка» — проверка свободного места, создание окружения (`uv`, изолированный Python 3.12), установка колёс по locks, загрузка моделей по зафиксированным revision, прогресс и логи. Права администратора не нужны. Глобальный Python не трогаем.
- Каталоги: окружения `%LOCALAPPDATA%/komaflow/sidecar/envs`, модели `…/models`, кэш MIOpen `…/cache/miopen` (**постоянный**, переживает перезапуски).
- Выбор бэкенда: определить GPU через `torch` (`gcnArchName`); `gfx1031` (и родственные gfx1030/gfx1032) → `rocm`; иначе `cpu`. Колёса ROCm для Windows — из репозиториев AMD / TheRock (см. locks бенчмарка).

## 11. Модели и результаты замеров на целевом железе

Замеры из бенчмарка пользователя (RX на gfx1031, Windows, веса safetensors, без ONNX):

| Модель | Вариант | Время на страницу | Пик VRAM |
|---|---|---|---|
| `mayocream/koharu-layout-highres` | ROCm, fp32 + блочное внимание | ~3,4 с | ~7,6 ГБ |
| `PaddlePaddle/PaddleOCR-VL-1.6` | ROCm, fp16, `use_cache=True` | ~24 с (вся страница) | ~9,4 ГБ (резерв PyTorch ~10,8) |
| `mayocream/lama-manga` | ROCm, fp32, вся страница | ~0,29 с | ~3,1 ГБ |

- Первый вызов намного дороже (LaMa ~26 с, OCR ~31 с, layout ~7 с): прогрев ядер MIOpen. Нужен постоянный кэш и, по возможности, прогрев в фоне при старте.
- CPU: layout ~25 с на страницу, LaMa ~9,5 с; OCR на CPU непрактичен (первая страница ~270 с). На CPU OCR отключается.
- DirectML исключён: layout не запускается, LaMa падает на FFT, у OCR сдвигаются блоки.
- LaMa в MVP **не используется**; установка опциональна (задел под автоклин).

**Обходные решения обязательны** (без них не работает): для layout — блочное внимание (`qchunk`, блоки по 2048 запросов; без него SDPA на ROCm gfx1031 строит полную матрицу внимания и падает по памяти); для OCR — `use_cache=True` (в `generation_config.json` модели стоит `false`, без кэша страница не обрабатывается).

**Один тяжёлый этап в VRAM за раз.** Все три модели вместе не помещаются в 12 ГБ, а OCR один занимает почти всё. Поэтому:
- каждый этап (`layout`, `ocr`) выполняется в **отдельном дочернем процессе**, который завершается после этапа и гарантированно освобождает VRAM;
- пакетная задача: сначала этап layout по всем страницам, потом этап OCR по всем кропам; модели не перезагружаются на каждую страницу;
- интерфейс десктопа (WebView2) тоже потребляет видеопамять: пик OCR должен оставлять запас; если памяти не хватает, снижается размер пакета/кропов.

## 12. Конвейер анализа

1. **Layout:** страница → боксы с классами и оценками. Классы модели (`id2label`) сопоставляются с нашими типами через `class_map` (файл-конфиг; сопоставление фиксируется в спайке S2). Неизвестные классы отбрасываются, порог по оценке настраивается.
2. **Кропы:** для каждого бокса вырезается область с отступом `ocr_padding_px` (стартовое значение подбирается в S2).
3. **OCR (по кропам):** каждый кроп отдаётся PaddleOCR-VL с OCR-промптом по model card; результат — `source_text` (переносы строк сохраняются). Режим по целой странице остаётся запасным.
4. Результат упаковывается в объекты; десктоп применяет авто-порядок.

## 13. Тесты сайдкара
pytest: контракт API (схемы), отмена задач, освобождение процессов, выбор бэкенда по заглушке устройства, сопоставление классов. Интеграционные прогоны на GPU помечаются маркером и не обязательны в обычном CI.
